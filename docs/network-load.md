# 通信負荷の見積もり（500同時接続）

2026-09-30時点の実装をもとにした導入検討用の概算です。実測値や性能保証ではありません。帯域は10進表記（1 KB = 1,000バイト、1 Mbps = 1,000,000ビット/秒）とします。

500人が接続して待機するだけなら、通信負荷は小さいと見込まれます。利用中の負荷は、投稿・更新の頻度、配信先の接続数、HTTPで再取得するデータ量で変わります。添付ファイルは扱いません。

## 現行実装の通信

- 接続維持：サーバーは45秒ごとに空のWebSocket Pingを送り、クライアントのPongを受け取ります。
- 投稿：WebSocketでチャンネルID・連番などを通知し、クライアントはHTTPで未取得の本文を取得します。
- 別チャンネルの投稿：チャンネル一覧を再取得します。通知処理に必要な本文取得も発生し得ます。
- 入力中表示：入力中のクライアントは2秒ごとに通知します。サーバーは閲覧権限のある接続へ中継します。現在そのチャンネルを表示していない接続にも配信されます。
- 接続状態：メンション候補を開いて購読している接続へ、接続状態の一覧を通知します。接続変化は約250ミリ秒単位でまとめます。
- リアクション・スレッド・アンケート・予定調整など：イベント通知に加え、必要な状態のHTTP取得が発生します。

実装の参照先は [サーバー](../internal/realtime/hub.go)、[チャット画面](../web/js/app.js)、[設計](../DESIGN.md)です。WebSocketのPing/Pongとフレーム形式は [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html#section-5)を参照してください。

## 待機時

500人がそれぞれ1本の接続を維持すると、平均で毎秒約11回のPingと、その応答が発生します。

```text
500接続 ÷ 45秒 ≒ 11.1往復/秒
```

TCPの確認応答、Ethernet、TLSなどを含め、1往復を合計約200～500バイトと仮定すると、送受信合計で約0.02～0.05 Mbpsです。これは接続維持だけの平均値であり、画面操作や他の定期通信は含みません。接続時刻がそろうとPingも一時的に集中します。

## 投稿時

WebSocket通知とHTTPリクエスト・レスポンス等を合わせた転送量を、1接続・1投稿あたり2～5 KBと仮定します。この値は計算例のための仮定で、本文長、チャンネル一覧の大きさ、表示画面、通知設定、追加API呼び出し、圧縮などにより変わり、上限ではありません。

```text
通信量（Mbps）≒ 毎秒の投稿数 × 配信先接続数 × 1接続あたりの転送量（バイト）× 8 ÷ 1,000,000
```

| 投稿頻度 | 配信先接続数 | 通信量の概算 |
| --- | ---: | ---: |
| 毎分10件 | 500 | 約1.3～3.3 Mbps |
| 毎秒1件 | 500 | 約8～20 Mbps |
| 毎秒1件 | 50 | 約0.8～2 Mbps |

これはサーバーとクライアント間の送受信を合計した目安です。多くはサーバーからの送信になります。全二重ポートの利用率は送信・受信を別々に評価してください。各端末の負荷がこの合計値になるわけではなく、配信対象が500接続の場合、1接続の負荷はおおむねその500分の1です。

## 入力中表示と一時的な集中

同じチャンネルで20接続が入力中で、約500接続へ中継する場合、2秒ごとの通知だけでも次の配信量になります。1配信200～400バイトはプロトコル付加分を含めた仮定です。

```text
20入力接続 ÷ 2秒 × 約500配信先 × 200～400バイト × 8
  ≒ 8～16 Mbps
```

実際には送信ユーザー自身の接続への中継は除外されます。開始・停止イベントや送信元からサーバーへの通信は別途加わります。大人数チャンネルでは、投稿が少なくても入力中表示が帯域を使う可能性があります。

一斉起動時は静的アセット、チャンネル一覧、初期履歴を取得します。一斉再接続時は取り逃した履歴を取得します。例えば500接続がそれぞれ100 KBを取得すると合計50 MB（400 Mb）となり、10秒間で転送すれば平均40 Mbpsです。これはサイズを仮定した計算例であり、現行画面の実測サイズではありません。

複数タブや予定調整画面などで接続が増えるため、500ユーザーが必ず500接続になるとは限りません。

## 既存ネットワークへの影響

空き帯域のある1 Gbps有線LANでは、通常のテキストチャットの負荷は小さいと見込まれます。100 Mbpsの共用回線では、8～20 Mbpsは回線容量の8～20%相当となるため、既存業務の通信と合わせて評価します。

通信はサーバー接続ポートと、端末までの経路に集中します。別拠点の回線、VPN、Wi-Fi、リバースプロキシ、ファイアウォールを経由する場合は、その区間の空き帯域と同時接続数も確認します。Wi-Fiでは小さいパケットの多発や再送も影響するため、有線の公称帯域だけでは判断できません。

この見積もりはネットワーク負荷を対象としています。500接続を処理するサーバーのCPU・メモリ・保存処理・HTTP応答性能は別途検証します。

## 導入前の実測

実際のチャンネル数・本文長・通知設定・TLS・プロキシ構成で、次を確認します。

| 条件 | 確認する負荷 |
| --- | --- |
| 500接続で待機 | 接続維持の平均値とPing集中時のピーク |
| 500接続宛てに毎分10件／毎秒1件を投稿 | 通知とHTTP取得の合計、投稿から表示までの遅延 |
| 同じチャンネルで20接続が同時入力 | 入力中イベントの配信量 |
| 500接続の一斉起動・再接続 | 初期取得・履歴取得のピーク、復旧時間 |
| 運用時の複数タブと他機能の利用 | 実際の接続数、追加API通信 |

サーバーの送受信バイト数、パケット数、短時間のピーク、HTTPリクエスト数、WebSocket切断・再接続数を記録します。サーバー接続ポートと共用回線で既存業務の通信量も測り、遅延・再送・切断が増えないことを確認します。ブラウザの転送サイズだけではTCP等の付加分を含めた回線上の通信量は分からないため、ポート統計等も使用します。

測定記録には接続数、配信先数、投稿頻度、入力中人数、本文長、チャンネル数、測定時間、ネットワーク構成を併記してください。負荷が大きい場合は、実測した内訳に応じて入力中通知の配信対象・間隔やHTTP再取得のまとめ方を検討します。
