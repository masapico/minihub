# リリースビルドと手動公開

## ビルド環境とコマンド

Go 1.27以降とGitを使用し、リポジトリのルートで実行します。Windows・macOS・Linuxで同じコマンドを使用できます。通常の依存モジュールの取得にはネットワーク、取得後のビルドにはローカルのGoモジュールキャッシュが必要です。Cコンパイラーや外部のZIP／tarコマンドは不要です。

```bash
go run ./scripts/release -version v1.0.0
```

バージョンは必須で、`v1.0.0`または`v1.0.0-rc.1`形式です。4種類を`CGO_ENABLED=0`、`-mod=readonly`、`-trimpath`でビルドします。子プロセスの`GOOS`・`GOARCH`・`GOFLAGS`などはスクリプトで設定し、CPUはamd64のv1／arm64のv8.0を使用します。`GOCACHE`などのキャッシュ設定は引き継ぎます。

```text
dist/v1.0.0/
├── minihub_v1.0.0_windows_amd64.zip
├── minihub_v1.0.0_darwin_arm64.tar.gz
├── minihub_v1.0.0_linux_amd64.tar.gz
├── minihub_v1.0.0_linux_arm64.tar.gz
└── SHA256SUMS.txt
```

`release/README.md`は配布用READMEの原本です。実行ファイル、サンプル設定、静的なHTML／CSSマニュアル、ビルド情報、依存物のライセンスを同梱します。Windows版には既存のバックアップスクリプトも同梱します。Web UIは実行ファイルへ埋め込まれるため、別途コピーしません。

全アーカイブとチェックサムを一時ディレクトリで完成させてから、`dist/<バージョン>/`へまとめて移動します。通常の失敗時は一時ファイルを片付けます。同じバージョンの出力は上書きしません。再ビルドする場合は以前の出力を別の場所へ移動してください。強制終了で`dist/.<バージョン>.lock`や`.release-*`が残った場合は、ビルドが動いていないことを確認してから残ったファイルを削除します。

生成物はGit管理しません。作業ツリーに変更がある場合もビルドできますが、`BUILDINFO.txt`に`dirty: true`と記録します。正式公開にはコミット済みの変更がない状態で生成した成果物を使います。スクリプトはタグの作成やGitHubへのアップロードを行いません。

## 検証

公開対象のコミットで以下を実行します。race検出にはCGOとCコンパイラーが必要です。配布用ビルドのCGO無効化は子プロセスだけに適用されます。

```bash
go test ./...
go test -race ./...
go run ./scripts/release -version v1.0.0
```

スクリプトのテストは、アーカイブの内容、実行権限、チェックサム、不正なバージョン、既存出力、途中のビルド失敗を検証します。クロスビルドの成功と各OSでの起動検証は別々に確認してください。

1. 各配布物を対象のOS・CPUで展開し、`BUILDINFO.txt`とマニュアルのリンクを確認します。
2. サンプル設定をコピーし、テスト専用の管理者パスワード・空のデータディレクトリ・ポートを設定します。
3. `file`と`sqlite`それぞれで起動し、ログイン、チャンネル作成、投稿、Ctrl+Cによる停止、再起動後の履歴保持を確認します。方式ごとに別のデータディレクトリを使います。
4. Windowsでは別のPowerShellから`stop -config minihub.json -wait 60s`を実行し、停止を確認します。
5. 実設定、データ、ログ、証明書・秘密鍵が配布物に含まれていないことを確認します。

チェックサムは`SHA256SUMS.txt`と同じフォルダーで確認します。

Linux：

```bash
sha256sum -c SHA256SUMS.txt
```

macOS：

```bash
shasum -a 256 -c SHA256SUMS.txt
```

Windows（出力を`SHA256SUMS.txt`と比較）：

```powershell
Get-FileHash ./*.zip, ./*.tar.gz -Algorithm SHA256
```

## GitHub Releasesへの登録

1. 検証対象の変更をコミットし、`git status --short`で作業ツリーがクリーンであることを確認します。
2. 同じバージョン名でタグを作り、pushします。例：`git tag -a v1.0.0 -m "minihub v1.0.0"`、`git push origin v1.0.0`。
3. タグのコミットからビルドした成果物を使い、リポジトリのGitHub Releasesで「Draft a new release」を開いて、そのタグを選択します。
4. 変更内容、対応OS・CPU、検証した環境、必要な移行手順をリリースノートへ記載します。署名・公証のない圧縮ファイルでの配布であることも記載します。
5. `dist/<バージョン>/`内の4つのアーカイブと`SHA256SUMS.txt`を添付し、内容を確認して公開します。`-rc.N`版はpre-releaseに設定します。

利用者の更新手順は「停止→データと実設定のバックアップ→実行ファイルの差し替え→再起動」です。インストーラー、サービス登録、署名・公証、自動公開はこのスクリプトの対象外です。
