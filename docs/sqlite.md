# 保存方式の選択・移行・バックアップ

[資料の目次](README.md) / [管理者マニュアル](admin-manual.md)

## 保存方式を選ぶ

どちらも外部DBサーバーは不要です。設定ファイルの `storage.type` で選びます。省略時は `file` です。

| 方式 | 保存先と特徴 |
| --- | --- |
| `file` | データディレクトリ内のJSON・日付別JSONL。履歴の索引を起動時にメモリへ構築します。 |
| `sqlite` | データディレクトリ内の `minuhub.db`。永続索引から履歴を取得し、履歴全体をGoのメモリへ読み込みません。WALを使うためローカルディスクに置きます。 |

新規導入では初回起動前に次の設定を選べます。既存データがある場合は、設定値だけを切り替えず、下記の移行手順を使ってください。保存方式とデータが一致しない場合、起動は拒否されます。

```json
"storage": {
  "type": "sqlite"
}
```

`server.dataDir` の相対パスは設定ファイルのあるディレクトリが基準です。CLIで `-data` を明示した場合はその値が優先されるため、移行と通常起動で同じディレクトリを指定します。

## fileからSQLiteへ移行する

対応する移行方向は `file` → `sqlite` のみです。SQLiteからfileへ戻す変換コマンドはありません。一時DBを作るため、移行元のデータに加えてDBを置ける空き容量を確保してください。

1. サービスを停止し、プロセスの終了を確認します。macOS／Linuxでは前面起動ならCtrl+C、サービス管理下ならその停止操作を使います。Windowsでは `minihub.exe stop -config minihub.json -wait 60s` を使えます。
2. データディレクトリ全体と設定ファイルを、データディレクトリの外へバックアップします。
3. 設定の `storage.type` は `file` のまま、次のコマンドで検証します。

   ```bash
   ./minihub migrate -config minihub.json -to sqlite -dry-run
   ```

   検証は一時DBで行い、保存方式を切り替えません。JSON出力の `records` には種別ごとの件数と照合値が入ります。`incompleteTails` が出た場合は、そこに示されたログの改行で完結していない末尾を除外しています。必要な投稿が欠けていないか確認してください。完全行の破損や未対応のレコードはエラーとなります。

4. 検証成功後、実際に移行します。コマンドがエラーなく終了したことを確認します。

   ```bash
   ./minihub migrate -config minihub.json -to sqlite
   ```

5. 設定ファイルの `storage.type` を `sqlite` へ変更し、起動します。

   ```bash
   ./minihub -config minihub.json
   ```

6. ログイン、公開・非公開チャンネルの履歴、返信、未読、アンケート・予定調整を確認します。

Windowsでは各コマンドの `./minihub` を `minihub.exe`（PowerShellでは `./minihub.exe`）へ置き換えます。

移行は元のfileデータを変更せず、ID・連番・日時や関連イベントを引き継ぎます。移行後に残るfileデータは、その後の投稿を含まないため最新のバックアップとして使えません。

## 移行中にエラーや中断が起きた場合

サービスを停止したまま原因を確認します。DBの確定と保存方式の識別情報の更新の間で中断した場合は、同じ移行コマンドの再実行が確定済みDBを検証し、識別情報の更新を完了します。すでにSQLiteへの切り替えが完了している場合、再移行は拒否されます。無関係な既存DBも上書きしません。

`storage.json` やDBを手動で消して起動を通すことは避けてください。復旧できない場合は、移行前のバックアップを別の空ディレクトリへ丸ごと復元し、復元したデータに合う `storage.type=file` の設定で起動します。移行後に受け付けた投稿は、移行前バックアップには含まれません。

## バックアップと復元

両方式ともサービス停止後にデータディレクトリ全体をコピーします。SQLiteではDB本体だけをコピーせず、`storage.json`、残存するWALなどの関連ファイルも含めてください。設定ファイルも別途、アクセスを制限して保管します。

復元時もサービスを停止し、既存データと混ぜずに整合したバックアップ全体を戻します。設定の `storage.type` と `server.dataDir` を確認してから起動し、ログインと履歴を確認します。DB破損時にfile方式へ自動で切り替わることはありません。

Windowsの停止・ZIPバックアップは [管理者マニュアルの手順](admin-manual.md#windowsのバックアップ)を参照してください。投稿の物理削除は [削除手順](retention-proposal.md)に従って停止中に実行します。

実装の詳細は [DESIGN.md](../DESIGN.md)、両方式の試験や移行・復元の検証方法は [テストの説明](../tests/README.md#sqlite共通試験と移行試験)を参照してください。
