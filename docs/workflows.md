# 処理フロー

[設計図の目次](README.md) / [アーキテクチャ](architecture.md) / [データモデル](data-model.md)

以下のアクティビティ図は Mermaid のフローチャートで表しています。現行コードの主な分岐を示し、細かい入力制限や全APIを列挙するものではありません。

## ログインとチャンネル認可

```mermaid
flowchart TD
    A["POST /api/auth/login"] --> B["ユーザーID・パスワードを検証"]
    B --> C{"有効な利用者か"}
    C -->|いいえ| X["認証エラー"]
    C -->|はい| D["トークンのハッシュとCSRF値を含むセッションを保存"]
    D --> E["CookieとCSRF値を返す"]
    E --> F["後続のHTTP API / WebSocket"]
    F --> G["セッションを認証"]
    G --> H{"更新要求か"}
    H -->|はい| I["CSRF値を確認"]
    H -->|いいえ| J["サービス層で権限判定"]
    I --> J
    J --> K{"対象チャンネルを使えるか"}
    K -->|はい| L["処理を実行"]
    K -->|いいえ| M["閲覧不可・投稿不可を返す"]
```

公開チャンネルは非参加者も閲覧できますが、投稿には参加が必要です。非公開チャンネルの閲覧・投稿は直接参加者または割当グループの有効な所属者に限ります。アーカイブ中は通常の閲覧・投稿ができません。管理操作は管理者または対象チャンネルの管理者に絞られます。

## チャンネル参加と投稿

```mermaid
flowchart TD
    A["利用者が公開チャンネルへの参加を要求"] --> B["認証・公開状態を確認"]
    B --> C{"公開中の公開チャンネルか"}
    C -->|いいえ| X["拒否"]
    C -->|はい| P{"まだ実効メンバーではないか"}
    P -->|はい| Q["現在の最新seqを初期既読位置に保存"]
    P -->|いいえ| D["Channel.Membersを更新して保存"]
    Q --> D
    D --> E["channels_changedを配信"]
    E --> F["利用者が本文を投稿"]
    F --> G["投稿権限・文字数・メンション宛先を検証"]
    G --> H{"検証成功か"}
    H -->|いいえ| X
    H -->|はい| I["Storage.AddMessageで採番・永続化"]
    I --> J{"保存成功か"}
    J -->|いいえ| Y["保存エラーを返す・通知しない"]
    J -->|はい| K["投稿者の本流既読位置を更新"]
    K --> L["new_messageを配信"]
    L --> M{"既読更新は成功したか"}
    M -->|はい| N["投稿結果を返す"]
    M -->|いいえ| O["コミット済みエラーを返す<br/>同じ投稿を自動再送しない"]
```

初参加でまだ実効メンバーでない場合は、参加時点の最新連番を既読位置に設定します。退出はチャンネル管理者には許可されません。本流投稿の `AddMessage` が成功した後、投稿者の既読更新と通知が行われます。既読更新に失敗しても投稿は取り消されず、通知は配信されます。スレッド返信は起点の存在と取消状態を確認し、同じチャンネル連番で保存した後に `thread_updated` を配信します。返信時に本流の既読位置を進める処理はありません。

## グループ所属の管理

```mermaid
flowchart TD
    A["管理者がグループ所属の差分を送る"] --> B["管理者権限と対象グループ・ユーザーを確認"]
    B --> C{"入力は有効か"}
    C -->|いいえ| X["変更せずエラー"]
    C -->|はい| D["対象ユーザーのUser.Groupsを更新"]
    D --> E["ユーザーごとのJSONまたはSQLite行を保存"]
    E --> F["更新後のグループ詳細を取得"]
    F --> G["channels_changedを配信"]
    G --> H["以降の閲覧・投稿権限へ反映"]
```

所属の正本は `User.Groups` です。複数ユーザーへの保存はユーザー単位で進み、途中の永続化失敗時に一括ロールバックされる契約ではありません。

## 投稿から通知・取得までのシーケンス

```mermaid
sequenceDiagram
    participant B as ブラウザ
    participant A as HTTP API
    participant S as Service
    participant D as Storage
    participant W as WebSocket Hub
    participant R as 他の閲覧可能なブラウザ
    B->>A: POST /api/channels/{id}/messages
    A->>A: セッションとCSRFを確認
    A->>S: PostMessage
    S->>S: 投稿権限・本文・メンションを確認
    S->>D: AddMessage
    D-->>S: コミット済み seq / id
    S->>D: 投稿者の既読位置を更新
    S->>W: NewMessage(channelId, seq)
    W->>W: 接続先の閲覧権限を確認
    W-->>R: new_message(channelId, seq)
    S-->>A: 投稿結果
    A-->>B: HTTP応答
    R->>A: GET /api/channels/{id}/messages?after=...
    A->>S: GetMessages
    S->>D: 必要な本文とスレッド要約を取得
    D-->>S: ページ
    S-->>R: 閲覧可能な内容
```

WebSocketイベントは履歴本文を複製しません。接続していない間の投稿も、再接続時にHTTP APIで取得します。通知は保存済みデータの存在を知らせる手段で、履歴の正本ではありません。

## 既読と再接続

```mermaid
flowchart TD
    A["ブラウザが再接続"] --> B["セッションでWebSocketを再確立"]
    B --> C["閲覧可能チャンネルの既読・未読状態を取得"]
    C --> D["前回位置より新しい本流メッセージをHTTPで取得"]
    D --> E["開いているスレッドの要約と不足返信を取得"]
    E --> F["表示したメッセージのseqで既読更新を要求"]
    F --> G["権限と対象seqの存在を確認"]
    G --> H["保存済みのlastReadSeqより大きい場合だけ更新"]
```

本流の未読数は既読位置より新しい本流投稿から計算します。スレッドは起点ごとに返信の既読位置を持ち、未読や更新の表示を別に計算します。古いクライアントからの更新で既読位置は後退しません。メンション確認時刻もユーザー状態として保存されます。

## 投票・予定調整の状態

```mermaid
stateDiagram-v2
    state "投票: open" as PO
    state "投票: closed" as PC
    [*] --> PO: 作成・告知投稿
    PO --> PO: 回答・回答変更
    PO --> PC: 手動終了
    PO --> PC: 期限到達時は表示・回答可否で終了扱い
```

投票回答はイベントを追記し、ユーザーの最新回答で集計します。期限到達による `closed` は表示・回答可否の判定であり、必ずしも保存済み `status` の書き換えを伴いません。回答の競合は前回回答の連番で検出します。

```mermaid
stateDiagram-v2
    state "draft" as D
    state "open" as O
    state "closed" as C
    state "finalized" as F
    [*] --> D: 下書き作成
    D --> O: 公開・告知投稿
    O --> C: 手動終了または期限到達
    C --> O: 再開
    O --> F: 候補を確定
    C --> F: 候補を確定
```

予定調整の回答は候補ごとの選択とコメントを履歴に追記し、最新回答を採用します。公開・確定時にはチャンネルに参照付き告知メッセージを投稿します。取消はどちらの業務データでも別の `Withdrawal` 記録で管理し、元の状態と履歴を物理削除しません。チャンネルのアーカイブもメタデータ変更です。

## 取り消し・復元

```mermaid
flowchart TD
    A["メッセージ・投票・予定調整の取消要求"] --> B["閲覧権限と取消権限を確認"]
    B --> C{"対象と操作は有効か"}
    C -->|いいえ| X["エラーを返す"]
    C -->|はい| D["Withdrawalへ取消イベントを保存"]
    D --> E["対象変更の通知を配信"]
    E --> F["通常APIでは内容を伏せた表示を返す"]
    F --> G["許可された利用者が復元を要求"]
    G --> H["Withdrawalへ復元イベントを保存"]
    H --> I["対象変更の通知を配信"]
    I --> J["元の保存内容を再び表示"]
```

投稿本文と投票・予定の元レコードは書き換えず、取消の状態と履歴を別に持ちます。投票・予定の告知投稿はそれぞれの取消APIから扱い、通常メッセージの取消APIでは扱いません。

## 停止中の file → SQLite 移行

```mermaid
flowchart TD
    A["サービスを停止"] --> B["minihub migrate -to sqlite を実行"]
    B --> C["dataDirの排他ロックを取得"]
    C --> D["fileデータを変更せず順次読み込み"]
    D --> E["一時SQLite DBへID・seq・時刻・履歴を移す"]
    E --> F["件数・ダイジェスト・参照・DB整合性を検証"]
    F --> G{"検証成功か"}
    G -->|いいえ| X["移行失敗・file方式を維持"]
    G -->|はい| H["正式なminuhub.dbとして確定"]
    H --> I["storage.jsonをsqliteへ更新"]
    I --> J["設定のstorage.typeをsqliteへ変更して起動"]
    H -.->|"確定後に中断"| R["再実行でDBの完了情報を検証し、識別情報を修復"]
    R --> I
```

`-dry-run` は同じ検証を一時DBで行い、方式を切り替えません。移行元のfileデータは残ります。復旧やバックアップの詳細は [DESIGN.md](../DESIGN.md) の「SQLite保存方式」を参照してください。
