投稿の物理削除

目次
  • 日付とコマンド
  • 対象と保存データ
  • 実行と復旧

投稿の物理削除は、サービス停止中に管理コマンドで実行します。管理画面やサーバー起動時には実行しません。手動実行、またはタスクスケジューラ／cronからの実行を想定します。

日付とコマンド

設定ファイルへ "retention": { "days": 365 } を追加すると、保存日数を指定できます。省略または 0 は無効です。-policy は実行日の日本時間の日付から暦日で指定日数を差し引きます。-before は任意の削除基準日です。両者は併用できません。

minihub retention -config minihub.json -policy
minihub retention -config minihub.json -policy -apply
minihub retention -config minihub.json -before 2025-01-01
minihub retention -config minihub.json -before 2025-01-01 -apply

-apply を省くと対象件数だけをJSONで表示します。両方式とも、日本時間で基準日の00:00より前に作成された投稿を削除し、基準日当日の投稿は残します。出力の messages は返信と告知を含む削除投稿数、polls と schedules は削除する本体数です。設定変更はサービスの再起動後に反映されますが、削除コマンドは実行時に設定を読みます。

対象と保存データ

  • 親投稿が対象なら、そのスレッドの新しい返信も削除します。親が残る場合は期限に達した返信だけを削除します。
  • 投票・予定の告知が対象なら、その本体、回答、ほかの告知も削除します。対象投稿のリアクション、メンション確認、取り消し履歴も削除します。
  • 通常の既読位置は後退させず、未読件数は残った投稿から求めます。削除した親のスレッド既読状態は消します。投稿IDとチャンネル内連番は再利用しません。
  • file方式は日付別JSONLを安全に再構成し、channels/<id>/sequence.json に採番上限を保持します。このファイルはバックアップとfile→SQLite移行にも含めます。SQLite方式は関連行をトランザクションで消し、WALを整理して VACUUM で領域を回収します。

実行と復旧

  1. サービスを停止し、データディレクトリ全体の整合したバックアップを作成します。Windowsの既存 scripts/backup.bat は停止とZIP作成までを行います。
  2. -apply なしで対象件数を確認し、同じ引数に -apply を付けて実行します。成功後は retention-runs.jsonl に基準日と件数が記録されます。
  3. 履歴、未読、投票・予定、ログインを確認してからサービスを起動します。定期実行ではこの順序をタスクスケジューラ／cronのジョブにします。

処理が中断した場合、通常起動は保留されます。同じ基準日で -apply を再実行して完了させてください。-policy は日付が変わると基準日も変わるため、中断時は出力に表示された基準日を -before へ指定します。バックアップから戻す場合は、データディレクトリを丸ごと復元し、部分的なファイルだけを混ぜないでください。

既存のバックアップZIPは削除コマンドの対象外です。バックアップ保存期間は別途管理してください。SQLiteの VACUUM は元DBの約2倍の空き容量を必要とする場合があります。
