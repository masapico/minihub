導入と日常管理の要点です。チャットの使い方はユーザー向け操作マニュアルを参照してください。

初期設定と起動

  1. minihub.sample.jsonを実際に使うminihub.jsonへコピーし、initialAdmin.passwordを8文字以上・UTF-8で72バイト以下の値に変更します。実設定ファイルには管理者だけがアクセスできるようにしてください。
  2. minihub -config minihub.jsonで起動し、設定した管理者IDとパスワードでログインします。
  3. 初期管理者の作成を確認したら、実設定ファイルからinitialAdminブロックを削除します。

storage.typeはfileまたはsqliteです。省略時はfileで、SQLiteもデータディレクトリ内に保存します。保存方式を変更する際は、設定値だけを切り替えず、停止中に保存方式の選択・移行手順を実行してください。

HTTP／HTTPSは設定で一方を選びます。server.tls.enabledを省略するかfalseにするとHTTPです。HTTPSではtrueにし、server.tls.certFileとserver.tls.keyFileへPEM形式の証明書と秘密鍵のパスを指定します。相対パスは設定ファイルの所在ディレクトリが基準です。ポートはserver.listenAddressで指定します。HTTPSではSecure Cookieが自動で有効になります。リバースプロキシでHTTPSを終端する場合はSecure Cookieを明示的に有効にします。証明書の信頼設定、秘密鍵のアクセス権、証明書更新の手順はHTTP／HTTPSの選択を参照してください。証明書や秘密鍵が不正なら起動を中止します。

notifications.osNotificationsEnabledは省略時trueです。falseではOS通知ボタンが無効になり、管理者設定による利用不可を表示します。利用者が以前ONにしていてもOS通知を停止します。アプリ内通知と未読表示は継続します。trueでも利用者自身のON操作とブラウザの許可が必要です。OS通知の接続元と管理対象Edgeの設定はブラウザAPIを使ったOS通知の設定を参照してください。設定変更と証明書更新後はサービスを再起動し、開いている画面を再読み込みします。

ビルドと初回起動

Go 1.27以降が必要です。macOS／Linuxでは次のようにビルドします。

go build -o minihub ./cmd/minihub

Windows PowerShellでは次のように準備します。

go build -o minihub.exe ./cmd/minihub
Copy-Item minihub.sample.json minihub.json

minihub.jsonのinitialAdmin.passwordを変更してから、./minihub.exe -config minihub.jsonで起動します。実設定はGit管理せず、管理者と実行アカウントだけが読み取れる権限にしてください。

macOS／Linuxの初期設定

推奨セットアップはサンプル設定のコピーです。初期パスワードを記入した実設定はGit管理せず、所有者だけが読めるようにしてください。

cp minihub.sample.json minihub.json
chmod 600 minihub.json

initialAdmin.password を8文字以上・UTF-8で72バイト以下に変更して初回起動します。管理者作成後は initialAdmin ブロックを minihub.json から削除してください。設定ファイルがない場合は、従来どおり次の環境変数でも初期化できます。

初回起動では、管理者 admin を自動作成します。パスワードをシェル履歴へ残さないよう、次のように入力して起動してください（8文字以上、UTF-8で72バイト以下）。

printf 'admin のパスワード: '
read -r -s MINIHUB_ADMIN_PASSWORD
export MINIHUB_ADMIN_PASSWORD
echo
./minihub -addr 127.0.0.1:8080 -data ./data
unset MINIHUB_ADMIN_PASSWORD

環境変数方式では次の初期ユーザーを作成します。設定ファイル方式では initialAdmin.id と name を使用します。パスワードはユーザーJSONへ平文では保存されません。

ユーザーID表示名ロール
admin管理者管理者

この自動作成はデータディレクトリにユーザーが一人もいない場合だけ実行されます。2回目以降の起動では MINIHUB_ADMIN_PASSWORD は不要で、既存ユーザーのパスワードも変更されません。

起動オプション・表示設定

設定ファイルを明示して起動する方法を推奨します。ビルド済みファイルから起動する場合:

./minihub -config minihub.json

ソースから起動する場合:

go run ./cmd/minihub -config minihub.json

-config には使用する設定ファイルのパスを指定します。設定ファイル内の相対的な dataDir は、設定ファイルの所在ディレクトリを基準に解決されます。設定変更後はサービスを再起動してください。

通常起動時のサーバーログは server.dataDir/server.log に JSON 形式で追記します。-data を指定した場合は、そのディレクトリの server.log に出力します。再起動時に既存のログは消去されず、ローテーションも行いません。設定を読み込めない場合やログファイルを開けない場合のエラーは、標準エラーに表示します。

-config を省略した場合は、カレントディレクトリの minihub.json があれば自動的に読み込みます。明示した設定ファイルがない場合や、読み込んだ設定が不正な場合はエラーになります。初期管理者の環境変数は MINIHUB_ADMIN_PASSWORD を使用します。設定ファイルがない場合は、次のように待受アドレスとデータディレクトリをCLIフラグで指定できます。

./minihub -addr 127.0.0.1:8080 -data ./data

閉域内の他のパソコンから接続させる場合は、すべてのIPv4ネットワークインターフェースで待ち受ける0.0.0.0:8080を指定します。起動中の場合は一度停止してから実行してください。

# Windows（PowerShell）
./minihub.exe -config minihub.json -addr 0.0.0.0:8080
# macOS／Linux
./minihub -config minihub.json -addr 0.0.0.0:8080

設定ファイルのserver.listenAddressを"0.0.0.0:8080"へ変更する方法もあります。明示した-addrは設定ファイルの値より優先されます。ファイアウォールでは必要な閉域内の接続元からTCP 8080へのアクセスを許可します。他のパソコンからは、サーバー機のIPアドレスが192.168.1.10の場合、http://192.168.1.10:8080/loginを開きます。

画面に表示するワークスペース名とログインフォームの案内文は、minihub.json の ui で設定できます。workspaceTitle は通常画面左上、ログイン画面のブランド名、ブラウザタイトルに反映されます。設定変更後はサービスを再起動してください。

"ui": {
  "workspaceTitle": "社内チャット",
  "loginMessage": "会社のアカウントでログインしてください。"
}

共有フォルダーやファイルの案内方法は features.networkPathMode で設定します。既定の copy では、UNCパスをアイコン付きの共有場所として表示し、利用者がパスをコピーできます。

"features": {
  "selfPasswordChange": true,
  "networkPathMode": "copy"
}
  • disabled: 新しい共有パスの挿入を無効化します。過去の共有パスは読み取り可能な状態で表示します。
  • copy: 共有パスを挿入でき、パスのコピーボタンを表示します。
  • open-and-copy: コピーに加えて file:// の「開く」を表示します。管理されたブラウザ環境でだけ使用してください。

通常のHTTP/HTTPSリンクはどのモードでも利用できます。設定変更後はサービスを再起動してください。

明示した -addr、-data、-base-path、-secure-cookie は設定ファイルの値より優先されます。ただし、minihub自身のHTTPS待ち受けではSecure Cookieを必ず有効にします。設定を指定しない場合の既定値は、待受アドレスが 127.0.0.1:8080、データディレクトリが ./data です。別端末から接続させる場合は、ファイアウォールやリバースプロキシを適切に設定したうえで待受アドレスを変更してください。

リバースプロキシとベースパス

既存のWebサーバーに相乗りし、https://myhost.com/hub/ で公開する場合は、minihub.json の server に basePath を指定します。HTTPSをnginxで終端する例です。

"server": {
  "listenAddress": "127.0.0.1:8080",
  "basePath": "/hub",
  "dataDir": "data",
  "secureCookie": true,
  "sessionTTL": "12h"
}

basePath の省略、空文字列、"/" はドメイン直下での公開です。"/hub/" は "/hub" に正規化します。"/apps/chat" のような複数階層も使用できます。各階層には半角英数字と .、_、~、- を使用でき、空の階層、. と .. だけの階層、クエリ、フラグメント、パーセントエンコードは指定できません。不正な値は起動時にエラーになります。

CLIでは ./minihub -config minihub.json -base-path /hub と指定できます。明示した -base-path は設定ファイルより優先され、-base-path="" でドメイン直下へ戻せます。変更後はサービスを再起動し、画面を再読み込みしてください。

nginxの http コンテキストに次の map を追加します。

map $http_upgrade $minihub_connection_upgrade {
    default upgrade;
    ''      close;
}

証明書を設定済みの myhost.com のHTTPS server ブロックに、次の location を追加します。

location = /hub {
    return 308 /hub/$is_args$args;
}

location ^~ /hub/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $minihub_connection_upgrade;
    proxy_read_timeout 75s;
}

proxy_pass の宛先には末尾の / を付けず、/hub/ を保ったまま転送します。例えば /hub/api/me はminihubにも /hub/api/me として届く必要があります。ベースパスは設定値を使用し、X-Forwarded-Prefix からは推測しません。Host は外部のホスト名・ポートを保持し、Upgrade と Connection はWebSocket接続のために転送します。nginxの仕様は proxy_pass と WebSocket転送 を参照してください。

利用者は https://myhost.com/hub/ または /hub/login へアクセスします。予定調整一覧は /hub/schedules、詳細は /hub/schedules/<ID>、APIは /hub/api/...、WebSocketは /hub/api/realtime です。ローカルの待受先へ直接接続する場合も http://127.0.0.1:8080/hub/ のようにベースパスを付けます。ベースパス外のURLは404になります。

セッションCookieの送信範囲は /hub/ に限定します。ブラウザの表示設定・通知履歴・通知用Web Locksもベースパスごとに分けます。ドメイン直下では従来の保存キーを維持します。ベースパスを変更した場合は、新しいURLで再ログインし、表示設定やOS通知のON/OFFを設定し直してください。チャットデータの移行は不要です。

ログインとセッション

起動後、ブラウザで次のURLを開きます。

http://127.0.0.1:8080/login

未認証で / を開いた場合も /login へ移動します。初回起動で登録したユーザーIDとパスワードを入力してください。ログイン後の通常画面にはログイン用パスワード欄を含めず、画面左上のログアウトアイコンから別ユーザーへ切り替えられます。

ログインセッションの有効期間は12時間です。セッションはデータディレクトリの sessions/ に保存されるため、有効期間内であればサーバーを再起動してもログイン状態が維持されます。ブラウザへ渡す生のセッショントークンはファイルへ保存しません。

起動時、HTTP受付前に期限切れセッションを削除し、削除件数をログへ記録します。破損・期限欠落ファイルは保持し、読み込み・削除失敗は警告として記録して起動を継続します。定期掃除は行わないため、連続稼働中に期限切れになったファイルは、ログアウトなどの個別削除または次回起動時に整理されます。

HTTP／HTTPSの選択

minihub自身でHTTPSを待ち受ける場合は、設定ファイルの server に次の項目を設定します。

"listenAddress": ":8443",
"tls": {
  "enabled": true,
  "certFile": "certs/server.crt",
  "keyFile": "certs/server.key"
}

server.tls の省略、または enabled: false では従来どおりHTTPで待ち受けます。HTTPとHTTPSのどちらか一方を選択し、同時待ち受けやHTTPからの自動リダイレクトは行いません。ポートは listenAddress（または -addr）で明示します。HTTPS例のURLは https://<サーバー名>:8443/login です。最低TLSバージョンは1.2です。

証明書と秘密鍵はPEM形式で用意します。証明書ファイルには必要な中間証明書も含めてください。相対パスは設定ファイルの所在ディレクトリを基準に解決されます。証明書の名前が利用するサーバー名と一致し、有効期間内であり、組織のCAが利用者端末で信頼されていることを確認してください。秘密鍵はサービスの実行アカウントと管理者だけが読めるように権限を制限します。

証明書・秘密鍵の欠落、読み取り失敗、形式不正、組み合わせ不一致では起動を中止し、HTTPには切り替えません。証明書を自動発行・自動更新する機能はありません。設定変更や証明書更新後はサービスを再起動し、開いている画面を再読み込みしてください。証明書が利用できなくても停止・移行・保存期間の管理コマンドは実行できます。

minihub自身がHTTPSで待ち受ける場合は、セッションCookieの Secure 属性を必ず有効にします。secureCookie: false や -secure-cookie=false でも無効にはできません。リバースプロキシでHTTPSを終端し、minihubがHTTPで待ち受ける場合は、従来どおり server.secureCookie: true または -secure-cookie を指定します。

グループ管理

  1. 管理者メニューの「グループ管理」→「新規作成」で、部署やチームのIDと表示名を登録します。
  2. グループを選び、「ユーザーを追加」から所属ユーザーを選択します。所属解除や表示名の変更もこの画面で行います。
  3. 「割当チャンネル」で、そのグループが参加するチャンネルを確認します。

グループを削除するとユーザーの所属とチャンネルへの割当も解除されます。確認画面の影響件数を見てから実行してください。グループIDは変更できません。

グループの所属ユーザーと割当チャンネルを確認し、複数ユーザーを一括で追加・解除できます。グループIDには半角英数字、表示名には日本語を使えます。

ユーザー管理

  1. 管理者メニューの「ユーザー管理」で「新規登録」または「一括登録」を選びます。初期パスワード、権限、初期所属グループを指定します。
  2. 登録済みユーザーを選ぶと、表示名・パスワード・権限・ログインの有効／無効を変更できます。パスワードを変えないときは新しいパスワード欄を空欄にします。
  3. 登録後の所属変更は「グループ管理」で行います。

ユーザーIDは変更できません。ユーザー編集画面で所属グループは確認できますが、変更はグループ管理で行います。最後の有効な全体管理者を無効化・一般ユーザーへ変更する操作は拒否されます。

チャンネル管理

  1. 管理者メニューの「チャンネル作成」で表示名・ID・公開範囲を指定します。公開チャンネルにはユーザーが自由に参加でき、非公開チャンネルは設定された参加者だけが利用できます。
  2. 作成後、「チャンネル管理」で対象を選び、「個別参加メンバー」「参加グループ」「チャンネル管理者」を設定します。追加や解除を行ったら、最後に「変更を保存」を押します。
  3. 「基本設定」で表示名・公開範囲を変更できます。使わなくなったチャンネルは「アーカイブ」、再開時は「復元」を選びます。

グループ経由の参加者は、個別参加を解除しても利用を続けられます。チャンネル管理者を交代するときは後任を追加してから前任を外してください。アーカイブでは履歴は削除されません。

全体管理者以外にも、委任されたチャンネル管理者は担当チャンネルの参加者を管理できます。投稿・アンケート・公開済み予定調整の「取り消す」は保存データの物理削除ではありません。

チャンネル管理画面では「個別参加メンバー」「参加グループ」「チャンネル管理者」のタブで設定済み一覧を切り替え、名前・IDで検索、昇順で並べ替えできます。「追加」から候補を複数選択し、最後に「変更を保存」で反映します。個別参加メンバーには公開チャンネルへ自分で参加したユーザーも含みます。個別参加を解除しても、参加グループ経由の参加は継続します。

アーカイブしたチャネルは通常一覧から消え、履歴・投稿・既読・リアクション・予定調整へアクセスできなくなります。関連データは削除されず、復元すると再び利用できます。アーカイブ中も同じチャネルIDは再利用できません。

バックアップと復元

  1. サービスを停止し、書き込みが終わったことを確認します。
  2. 設定のserver.dataDirが指すデータディレクトリを、ファイルやサブディレクトリを含めて丸ごとコピーします。相対パスは設定ファイルのある場所が基準です。SQLiteではDB本体だけをコピーしないでください。
  3. 復元するときもサービスを停止し、整合したバックアップのデータディレクトリ全体を戻します。既存データと混在させず、設定の保存方式とデータが一致することを確認して起動し、ログインと履歴の表示を確認します。

稼働中のファイルをそのままコピーすると不整合になる可能性があります。バックアップからの復元を定期的に試してください。

古い投稿の物理削除は、サービス停止中にminihub retention -config minihub.json -policyまたは-before YYYY-MM-DDで対象件数を確認し、-applyを付けて実行します。実行前にデータディレクトリ全体をバックアップしてください。境界と中断時の再実行方法は投稿の物理削除を参照してください。

Windowsのバックアップ

Windowsでは scripts/backup.bat（リポジトリに同梱） でサーバーの停止とZIPバックアップを実行できます。冒頭の EXE、CONFIG、DATA_DIR、BACKUP_DIR を環境に合わせて編集してください。DATA_DIR は設定ファイルの server.dataDir と同じ絶対パスにします。 日本語を含むパスを指定する場合、バッチファイルは ANSI（日本語 Windows では CP932）で保存し、改行コードは CRLF にしてください。LF のまま保存すると cmd.exe が行を誤って解釈します。

コマンドプロンプトからは scripts\backup.bat を実行します。バックアップ後は minihub.exe -config minihub.json を手動で起動してください。

backup.bat は minihub.exe stop -config <設定ファイル> -wait 60s で停止を待ち、Windows標準の tar.exe でデータディレクトリ全体をZIP化します。途中のZIPは .partial.zip として作り、検査後に正式名へ変更します。スクリプトはサーバーを再起動しないため、失敗した場合も稼働状態を確認し、必要なら手動で起動してください。既存のバックアップは自動削除しないため、保存期間に応じて別途整理してください。 DATA_DIR がサーバーのデータディレクトリと一致していれば、server.log もZIPに含まれます。

バックアップ先はデータディレクトリの外に置いてください。共有フォルダーなら、バックアップを実行するWindowsアカウントにUNCパスで書き込み権限を与えてください。復元時はサーバーを停止し、ZIP内のデータディレクトリを元の場所へ展開してから手動で起動します。

AIアカウント

minihub.jsonのaiAccountsにOpenAI互換Chat Completions APIの接続先を追加して再起動します。llama.cppなどへ直接接続できます。省略・空配列では無効です。

"aiAccounts": [{
  "id": "assistant",
  "name": "社内アシスタント",
  "enabled": true,
  "url": "http://ai-server:8080/v1/chat/completions",
  "model": "local-model",
  "systemPrompt": "日本語で簡潔に回答してください。",
  "timeout": "120s",
  "token": "YOUR-AI-TOKEN"
}]

id・name・url・modelは必須です。urlは/v1/chat/completionsなどのパスを含む完全なURLを指定し、modelは接続先のモデル名（llama.cppでは--alias）に合わせます。任意のsystemPromptを先頭のsystemメッセージとして送ります。enabledの既定値はtrue、timeoutは120sです。tokenにBearerトークンを直接記載します（Bearer は付けません）。認証不要なら省略または空文字にします。空白のみや改行を含む値は指定できません。環境変数名を指定するtokenEnvも利用できますが、tokenとの両方に空でない値は指定できません。設定変更は再起動で反映します。URL・認証情報・モデル名・指示文はブラウザに公開しません。

トークンを含む実設定はGit管理せず、管理者と実行アカウントだけが読み取れる権限にしてください。Windowsではファイルの「プロパティ」→「セキュリティ」でアクセス権を設定します。Windows以外ではchmod 600 minihub.jsonを適用します。

全チャンネルで投稿可能なユーザーが利用でき、非公開チャンネルの内容も設定先へ送信されます。通常投稿からはその投稿のみ、スレッドからは親投稿と呼び出しまでの返信を送信します。取り消された本文とAIのエラー通知は除外します。呼び出し先AIの回答はassistant、人と別AIは投稿者情報付きのuserとして送信します。上限は親投稿込み1,000件・指示文を含む依頼JSON 1 MiBです。回答本文は16 KiB以内です。

同時実行4件・待機32件で、自動再送と再起動後の再開はありません。非ストリーミングのテキスト回答を取得し、空の回答や不正な応答は定型エラーとして通知します。タイムアウトでも外部で回答生成済みの場合があります。AI用のai_接頭辞は人ユーザーに使用できず、AI有効化時に既存ユーザーとの衝突を検査します。

SQLiteは起動時にスキーマv4へ更新します。事前に停止してデータディレクトリ全体をバックアップし、旧バイナリへ戻す場合は更新前バックアップを使用してください。llama.cppの起動例とHTTP契約はAI連携を参照してください。
